# 项目推进计划

状态：阶段一与阶段二已完成，可点击原型已获用户采纳，作为正式实现的交互与视觉基准。阶段 3.1 工程规范已获采纳，阶段 3.2 数据、接口与任务设计和阶段 3.3 工程基础 T00 已完成，下一任务为 T01 邮箱登录与个人外观。技术基础采用已确认的 Flutter、Dart、Go 及可扩展通知模块，登录方式已确定为邮箱验证码。

## 当前基础

产品支持 iOS 和 Android，采用统一品牌风格，服务中国大陆与海外用户，并允许跨地区互动。业务操作要求联网，首版提供站内通知。后端从初期支持统一账户和业务接口，为未来独立开发的微信小程序及更多通知渠道提供接入位置。

当前仓库包含业务词汇表、技术选型和通知模块设计。阶段一产出包括[产品规则](../product/rules.md)、[核心流程与状态](../product/flows-and-states.md)及[验收场景](../product/acceptance-scenarios.md)，已按确认后的规则完成校对。

## 阶段一：确定核心业务规则

已完成业务访谈，确定以下规则，并整理对应场景：

1. **空间与成员**：首批试用者为用户及其伴侣。独立账号可参与多个空间，成员平等，空间业务数据公开；新人接受邀请且全员同意后加入，老成员可直接返回。
2. **积分归属与使用**：余额按成员和空间独立记录。同空间积分可用于其他成员的小卖部，奖励新增积分，扣分和购买消耗积分；扣分可产生负余额，购买须余额足够。
3. **约定与记分**：约定指定适用成员和固定加减分值，可重复使用；任何成员可创建、修改和为适用成员记分，保存即生效。修改和撤销留痕，撤销按原值回退。
4. **购买与履行**：购买立即扣除单价乘以数量的总积分，按整笔完成、取消和全额退款；买卖双方任意一方可操作，历史完整保留。
5. **退出与数据保留**：成员自主退出，相关待完成购买整笔取消并退款；历史、余额和店铺设置保留，返回后恢复参与。重复请求与同时操作须保持记录和余额一致。

产出：产品规则稿、更新后的 `CONTEXT.md`、核心流程及状态说明，以及供原型和实现验证的验收场景。

完成情况：已用用户及其伴侣的示例流程，逐步说明从加入空间到完成一次积分购买的操作、可见内容、积分变化和购买状态；实际试用验证在后续阶段开展。

## 阶段二：交互设计、视觉设计与可点击原型

以已确认的业务规则为依据，依次完成页面结构、视觉方向和可点击原型。使用同一组示例数据展示用户与伴侣双方视角；多人空间沿用相同结构，通过成员选择覆盖差异。

### 2.1 页面结构与交互草图

确定主导航、空间切换、页面层级和每个页面的主要任务，整理核心操作的入口、步骤、结果与返回位置。用简单线框展示首页、约定与记分、小卖部与购买详情，并补充邀请加入、撤销、退款及退出恢复的入口。

产出：页面地图、页面清单、关键页面线框与交互说明，以及对应的验收场景。

完成情况：[页面结构与交互草图](../design/app-structure.md)已确认，覆盖首页、四个底部入口、顶部“我的”与空间管理，以及“约定与记分”“小卖部与购买”的表单、操作路径、返回位置和结果反馈。

完成标准：可以从页面入口逐步走通“加入空间 → 创建约定 → 记分 → 购买 → 完成或取消 → 查看通知”，清楚解释每一步的操作者、积分影响与反馈；页面结构得到用户确认。

### 2.2 视觉方向与关键页面设计

围绕统一品牌风格，确定整体气质、颜色、文字层级、图标、间距及关键控件。先设计首页、约定、小卖部和购买详情等代表页面，以真实业务文案、长昵称和多份购买内容检验一致性。iOS 和 Android 共用品牌表达，并适配各平台的返回、键盘、安全区域和系统交互。

用户已选择先生成关键页面设计图，在选定风格后制作可点击原型。

当前设计依据见[视觉设计任务说明](../design/visual-brief.md)。用户已选定带顶部文案和植物装饰的暖杏枝叶首页，全局方向保存在 [DESIGN.md](../../DESIGN.md)。[主题与配色](../design/themes.md)整理暖杏、青瓷、雾玫三套候选色表及装饰搭配；个人选择的主题应用到本人参与的全部空间。

暖杏主题的约定列表、记一笔、小卖部与购买详情已确认，见[关键页面设计](../design/core-pages.md)。购买和退款确认、约定表单、我的店铺、商品表单以及青瓷和雾玫的应用示例已确认，见[操作界面设计](../design/action-pages.md)。原型验证完整主题覆盖与设备适配。首版上线的主题数量随试用评审确定。

产出：关键页面视觉稿和设计规范，记录完整主题色表、装饰素材规则、文字层级、布局、控件及交互状态。使用 impeccable 的任务优先、信息层级、可访问性和原生交互指导设计。

完成标准：用户确认视觉方向；主要操作清楚，积分与状态可以通过文字理解，正常与长内容均可阅读，触控区域和文字缩放具备明确的适配要求。

### 2.3 完整可点击原型

将已确定的结构与视觉应用到核心页面，连接双方视角的完整流程。覆盖邀请加入、约定、积分明细、小卖部、购买详情及站内通知，以及关键的等待、余额不足、空状态、提交失败和重试反馈。

外观设置包含主题选择与预览，验证页面配色和首页装饰一起更新、跨空间沿用个人选择，并保持当前页面和操作内容。

产出：可在手机尺寸下操作的原型、更新后的页面清单和交互说明，以及原型验证记录。

当前产出见[原型使用说明](../../prototype/README.md)与[验证记录](../design/prototype-validation.md)。可直接打开单文件演示，或运行本地预览。演示数据保存在内存中，包含双方身份与第三位受邀成员，以及三套个人主题。

完成标准：试用者能找到下一步操作，理解积分变化原因，并辨认自己与对方的操作。完成一轮集中检查与修正，并记录实施时需要继续验证的问题。

## 阶段三：实现可在双端运行的完整流程

### 3.1 工程方案与规范确认

先确定首版登录与账号恢复方式、数据存储和图片存储方案，以及必要的技术依赖。明确账号、空间、约定、积分、购买与通知的模块接口和代码结构。内部账号与登录身份分开管理，为未来微信小程序接入保留位置。

统一前后端通信约定：请求和响应、错误码与 HTTP 状态、字段校验、权限失败、请求标识、重复提交和超时重试。用“余额不足”“请求重复”“购买状态已变化”等真实场景走通 Go 内部错误、接口响应、Flutter 提示和日志之间的关系。

确定 Go 和 Dart 的目录与模块组织、错误处理、日志与敏感信息规则、配置和数据库变更、格式化与静态检查、测试层次及依赖更新方式。Flutter 的主题、导航、网络访问与状态管理按已采纳原型落实。各项规范区分已确认选择和实施细则，用明确示例及可检查的标准完成一轮集中评审。

产出：[工程规范目录](../engineering/README.md)所列的方案与约定；对影响登录体验、运行成本和跨端兼容性的选择完成确认。完成标准：一条操作从客户端提交到服务端处理、返回错误、显示反馈和记录日志的行为可按文档复现；工程目录及检查命令有明确约定。

完成情况：六份工程规范已获采纳，见[评审记录](../engineering/review.md)。邮箱验证码登录、同邮箱恢复账号和优先复用现有服务器与 PostgreSQL 已纳入基线。

### 3.2 数据、接口与首轮任务设计

根据已确认的工程规范和业务规则，细化数据模型、权限、事务边界及第一条用户流程的接口契约。重点明确积分流水、购买扣分、退款、撤销和成员退出的一致性，并将请求与错误示例写进接口定义。

产出：[数据与事务模型](../engineering/data-model.md)、[首轮 OpenAPI 契约](../../api/openapi.yaml)和[实施任务 T00—T07](implementation.md)。任务按可演示的用户行为拆分，每项包含客户端、服务端与验证内容。

完成情况：36 条路径、45 个操作和 52 个 schema 已通过结构校验，17 组交换示例及 3 个无效输入已验证，见[设计检查](../engineering/contract-validation.md)。用户已确认链接／邀请码邀请和无人空间等待规则，验收基线补充 S08。

### 3.3 建立可运行的工程基础

依据确认后的页面结构、设计规范和原型，先建立最小工程基础：Flutter 应用、Go 服务、依据业务规则选择的数据存储与登录方案、数据库变更管理、配置和日志，以及基础构建与检查流程。建立一个可以随时演示的测试环境。

完成标准：Flutter 可在 iOS 和 Android 启动，能够访问 Go 服务；数据存储可初始化，主题与基础导航沿用已采纳原型，并有清楚的本地启动说明。

完成情况：T00 已建立 Flutter、Go 和隔离 PostgreSQL，两端模拟器均通过真实 HTTP 成功／错误及安全存储检查。精确版本、代码入口与验证范围见[工程基础](../engineering/foundation.md)，运行命令见 [README](../../README.md)。

### 3.4 按完整用户流程交付

以“两个账号建立关系 → 创建约定 → 按规则产生积分变动 → 在对方小卖部购买 → 按规则完成履行 → 查看站内通知”为第一条完整流程。

沿这条流程逐项实现客户端、服务端和必要的自动化检查。接口先定义请求、响应、权限、错误及重复请求语义，再完成双方实现。统一账户和通知模块从第一条流程开始使用。

产出：能安装到 iOS 和 Android 的测试版本，以及可复现的启动、构建和演示说明。

完成标准：两名参与者在真实设备上完成流程；积分记录与余额一致，权限符合规则，重复请求和网络超时重试的结果可解释，站内通知可查询。通知模块按已有设计验证事件恢复、去重和渠道扩展能力。

## 阶段四：小规模真实试用与首版发布

建议邀请三至五组符合首批目标人群的用户持续试用，并安排大陆与海外用户跨地区互动的样本。根据使用频率确定观察周期，跟踪邀请是否完成、约定是否持续使用、积分是否用于购买、商品或服务是否得到履行，以及用户需要帮助的位置。

依据反馈完善关键体验和错误处理，同时验证两端安装、升级、目标网络访问、数据备份恢复、账号及关系生命周期等行为。完成对应发布渠道所需的准备与验证。

产出：试用问题清单、按影响排序的改进任务、首版发布说明和运行维护说明。

完成标准：用户能够独立完成核心流程，积分和购买记录可靠，已发现的关键问题得到处理，维护者能定位错误并恢复服务。

## AI 辅助开发的工作方式

每项开发任务写清目标行为、涉及的规则、验收场景和完成标准。任务按可演示的用户行为拆分，逐项完成实现、检查和双端验证。

业务词汇保存在 `CONTEXT.md`，业务规则与流程保存在产品文档，工程约定保存在 `docs/engineering/`，需要记录理由的关键技术取舍保存在 ADR，具体执行任务保存在开发计划。根目录 `AGENTS.md` 为 AI 开发提供简短的规范入口。规则变化时同步更新对应文档和验收场景。

优先自动验证积分计算、购买状态变化、权限及重复请求处理等关键行为；界面在模拟器和真实设备上检查。每完成一项功能，都保留可运行的版本和清晰的变更记录。
