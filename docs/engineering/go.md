# Go 编码规范

状态：阶段 3.1 已获用户采纳。目录与依赖见[工程方案](architecture.md)，接口映射见 [API 规范](api.md)。

## 代码组织

按业务组织包和文件，公开方法表达完整操作。输入、返回值、权限前提、可返回错误和重复调用语义共同构成模块接口。简单操作直接实现；共享规则集中在实际调用方共同使用的位置。

HTTP handler 完成请求解析、身份取得、业务调用和响应输出。业务方法接收明确的操作者与命令参数，所有权限均在服务端验证。数据库行类型、HTTP DTO 和业务结果在有不同职责时分别定义。外部请求提供的操作者标识不得替代已验证身份。

接口定义在使用方，只包含实际需要的方法。优先保留具体类型；在外部依赖适配、真实实现差异或有价值的测试替换处提取小接口。依赖显式注入，配置在启动时验证并传入。

## 错误分类与传递

| 类别 | Go 内部表达 | 处理位置 |
| --- | --- | --- |
| 可预期业务结果 | 带稳定 `Code` 的业务错误，可包含安全的结构化参数 | HTTP 层查表转换为状态码和公开文案 |
| 字段问题 | 字段路径与错误码列表 | HTTP 层返回 422；解析失败返回 400 |
| 基础设施失败 | 用 `%w` 包装原始原因并补充操作上下文 | HTTP／worker 入口分类、记录及给出恢复方式 |
| 编程错误或 panic | 保留受控诊断信息 | 顶层恢复、记录并返回通用 500 |

使用 `errors.Is`／`errors.As` 识别错误。字符串用于诊断，业务分支依据类型或错误码。内部业务错误不包含 HTTP 状态，统一映射表由 `httpapi` 持有。

示例写法：数据库读取失败时返回 `fmt.Errorf("load purchase: %w", err)`；余额不足时返回 `BusinessError{Code: InsufficientPoints}`。`BusinessError` 的具体声明在实现中统一，公开参数按错误码逐项定义。HTTP 层用 `errors.As` 查找业务错误，对其余错误输出安全的 `INTERNAL_ERROR`。

数据库“无记录”由业务语义转换成资源不存在；唯一约束冲突仅对已知约束映射为业务结果；其他数据库错误保留为内部失败。处理返回的错误必须明确传播、转换或完成恢复，并在需要的位置说明原因。

同一失败由最终处理它的 HTTP 或 worker 入口记录一次。底层补充错误上下文并返回；内部原因经过脱敏后进入日志。对外响应只包含规范定义的安全字段。

## 事务、取消与后台任务

业务操作拥有事务，内部辅助函数接收同一个事务对象。空间写事务遵循“开始事务 → 锁空间 → 验证权限与幂等请求 → 读取当前数据 → 修改业务和流水 → 写事件与操作结果 → 提交”的顺序。

在业务写入前判定的拒绝可以作为该操作的终态结果保存，业务数据保持原值；处理策略见 API 规范。业务写入后的任何失败回滚整笔事务，所有数据库行及迭代错误均检查，回滚在未提交的退出路径执行。事务提交结果不明时，客户端仍使用原操作标识核对或重试。

`context.Context` 为首个参数，从请求传到数据库与外部依赖，设置合理的截止时间。worker 使用自身生命周期的 context，服务退出时停止领取新任务并等待当前短任务结束。每个 goroutine 都有明确的退出条件和错误接收者。

SQL 使用参数绑定；动态排序字段来自固定允许列表。对需要一致快照的查询显式选择读取策略。处理多项资源的操作保持固定访问顺序，外部调用放在数据库事务之外。

## 数据与风格

- Go 使用 `int64` 表达积分，所有乘法、加减法检查溢出及契约范围；积分计算使用整数。
- 时间由服务端记录为 UTC；面向用户的日期展示由客户端完成。
- 命名使用业务词汇，包名简短，小写文件名；公开方法的注释写明有价值的前提和副作用。
- `gofmt` 统一格式，`go vet` 与测试检查常见问题。SQL 和迁移在代码评审中一并检查。
- 新依赖写明解决的问题、维护情况、许可证与版本；常规工具能力优先使用已引入的库和标准库。
