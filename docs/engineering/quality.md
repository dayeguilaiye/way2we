# 检查与交付规范

状态：阶段 3.1 已获用户采纳。基础检查已接入根目录 Makefile；执行范围与证据见 [T00 验证记录](foundation.md#验证记录)。

## 每项任务的完成依据

任务写明目标行为、业务规则、涉及端点和验收场景编号。完成时提交代码、契约、必要的迁移和文档，说明执行过的检查及仍待真实环境验证的内容。功能按客户端、服务端和实际结果一起演示。

验证重点由风险决定：积分、权限、并发和恢复使用自动化检查；页面层级、系统返回、键盘、文字缩放及触控结合双端运行检查。测试覆盖行为与结果，保持实现细节可以调整。

## 检查矩阵

| 范围 | 检查内容 | 实施方式 |
| --- | --- | --- |
| Go 基础 | 格式、静态问题、模块测试和进程内数据竞争 | `gofmt`、`go vet ./...`、`go test -race ./...` |
| PostgreSQL 集成 | 实际事务、唯一约束、锁、回滚和并发结果 | 隔离测试数据库，真实 pgx 调用 |
| Flutter 基础 | 格式、类型与静态检查、状态和 Widget 测试 | `dart format`、`flutter analyze`、`flutter test` |
| API 契约 | 请求、成功及错误响应匹配 OpenAPI；旧客户端可解析 | `tools/check_contract.py` 使用 openapi-spec-validator 和 JSON Schema；服务实现后增加 HTTP 契约测试 |
| 数据库演进 | 空库建表、旧版本升级、约束与兼容性 | 执行真实 SQL 迁移并验证数据 |
| 双端流程 | 两个账号完成记分、购买、取消、通知 | iOS 和 Android 模拟器及真实设备 |
| 构建 | 依赖可恢复、两个平台产物可生成 | 固定工具链、依赖锁文件和构建配置 |

`go test -race` 检查进程内并发访问，数据库一致性通过真实并发事务验证。CI 执行相应检查并保留失败输出；本地提供相同入口。根目录提供 `make check`、`make test-integration`、`make dev` 等命令，依赖和工作目录见 [README](../../README.md)。

## 必须自动验证的行为

- C01：同一操作串行重试、并发提交、客户端超时和服务重启后，业务与积分只生效一次；同一标识改参数被拒绝。
- C02：余额 30 分同时购买两笔 20 分，至多一笔成功；验证原始余额、最终余额、流水和业务记录。
- C03：退出与购买、记分及成员变动同时执行，以同一空间生效顺序保证规则。
- C04：在业务变更、流水、事件和结果持久化的不同位置注入失败，验证整笔提交或回滚；提交后断线能查到原结果。
- A06—A08、P08—P12、L01—L06：撤销按原值、退款按实际支付、同一资源重复处理仅生效一次，退出与返回保留历史。
- S03—S06：跨空间访问、退出后的访问和操作限制，资源标识更换无法绕过权限。
- 通知：重复处理只生成一条站内通知，提交后重启可恢复；验证渠道适配接入位置。
- 登录：验证码过期、尝试次数、并发消费和重复身份注册；同邮箱恢复原账号；日志与响应不泄露凭据。
- Flutter：字段错误、余额不足、未知错误码、非 JSON 错误、登录到期和超时核对；切换账号／空间后旧响应不会污染当前页面。

场景编号来源于[业务验收基线](../product/acceptance-scenarios.md)。涉及数据库的测试使用独立实例或独立测试数据库，测试配置显式标记测试用途。

## 依赖与检查配置

提交 `go.mod`、`go.sum` 和 Flutter 应用的 `pubspec.lock`；构建工具版本固定在项目配置。格式化和静态检查配置随代码评审。新增规则先说明它发现的实际问题，再纳入检查；例外注明具体位置和原因。

升级依赖先读维护方变更说明，运行受影响检查，尤其关注登录、安全存储、路由、JSON 解析与数据库驱动。自动生成文件标明来源并通过固定命令再生成。

新增测试以公共业务操作为主要入口。针对真实数据库行为使用集成测试，纯规则使用快速测试；外部邮件与对象存储用可控适配器检查成功、失败及结果不明路径，并在测试环境做最小真实联通验证。

## 规范变更

跨端约定和关键技术变更先更新对应文档及评审清单，确认影响后实施；普通实现细节按既有规范直接完成。影响产品体验、运行费用、部署地区或数据可靠性的选择显式提交用户确认。格式和检查规则尽量交由工具执行。
