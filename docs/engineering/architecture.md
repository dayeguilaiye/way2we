# 工程方案

状态：阶段 3.1 已获用户采纳，作为工程实现基线。确认范围见[评审记录](review.md)。

## 技术栈与主要依赖

| 范围 | 当前选择 | 适合本项目的原因 |
| --- | --- | --- |
| 工程管理 | 同一仓库管理移动端、服务端、契约与文档 | 一次业务修改可连同两端和契约一起评审 |
| 服务端 | Go 标准库 `net/http`，一个部署单元 | 首版以 HTTP 业务接口和后台通知处理为主，入口与调用路径直观 |
| 数据库 | PostgreSQL，Go 使用 `pgx` 与显式 SQL | 余额、流水、购买和通知事件能够在同一事务中提交，约束和锁规则可直接检查 |
| 数据库变更 | goose 管理有序 SQL 迁移 | 本地、测试和正式环境按同一顺序建立结构 |
| 服务端日志 | 标准库 `log/slog`，JSON 输出 | 字段统一，按请求编号定位问题 |
| 移动端状态 | Riverpod（`flutter_riverpod`），按功能组织状态控制器 | 统一异步加载、依赖注入和账号／空间切换的状态生命周期 |
| 路由与网络 | `go_router`、Dio | 集中处理页面跳转、通知入口、鉴权、超时和上传 |
| 本机凭据 | `flutter_secure_storage` | 使用平台安全存储保存会话凭据 |
| 图片 | 私有对象存储，数据库保存对象标识和归属 | 图片权限与空间权限对应，历史购买可保留当时图片 |
| 接口契约 | HTTP JSON；OpenAPI 3.1 描述首轮接口 | 两端和未来小程序共用字段、错误语义与示例 |

具体版本已固定在构建配置与锁文件，见 [T00 工具链与工程基础](foundation.md)。用户已选择邮箱验证码登录，现有服务器和域名在国内，并有 PostgreSQL，预算较低。需要时可开通海外服务器。开发与先期试用优先复用现有资源；正式部署地区、数据库部署形态、邮件及图片存储供应商在接入前补齐。

### 依赖落实要求

上述主要库在 T00 按既定职责安装并验证。Go 的 `net/http`、`log/slog`、`errors` 属于标准库，随 Go 工具链版本管理；pgx、goose 以及 Flutter 插件记录其实际依赖版本。Go 使用 `go.mod`／`go.sum`，Flutter 应用使用 `pubspec.yaml`／`pubspec.lock` 保存依赖依据。

T00 同时记录 Flutter／Dart、Go、Xcode、Android SDK 的实际版本与支持目标，并生成静态检查配置和本地检查入口。功能开发需要引入辅助库时，在对应任务开始时写清库名、用途、兼容要求和验证方式；邮件和图片供应商 SDK 随接入方案确定。

## 工程目录与模块

采用以下目录，随实际功能创建有内容的文件：

```text
apps/mobile/                 Flutter 应用
  lib/app/                   应用装配、路由、主题
  lib/core/                  网络、会话、错误等共用能力
  lib/features/              按空间、约定、购买等功能组织
server/
  cmd/api/                   启动、依赖装配、优雅退出
  internal/httpapi/          HTTP 路由、DTO、鉴权及错误转换
  internal/account/          内部账号、登录身份、会话
  internal/space/            成员、约定、记分、店铺、购买、积分流水
  internal/notification/     通知事件、站内记录、投递处理
  internal/media/            图片上传、访问授权、对象存储适配
  internal/platform/         数据库连接、配置及日志初始化
  migrations/                SQL 迁移
api/openapi.yaml             机器可检查的接口契约
docs/engineering/            当前工程方案和规范
docs/adr/                    关键技术决定的取舍理由
```

`space` 是承载空间业务的模块，按 `members.go`、`agreements.go`、`scoring.go`、`purchases.go`、`ledger.go` 等文件组织行为。对外提供 `RecordScore`、`CreatePurchase`、`CancelPurchase`、`LeaveSpace` 等操作；调用方提交一次业务意图，模块完成权限、状态、积分和事件处理。积分流水写入集中在模块内部，方便购买、撤销和退出共用一致性规则。

HTTP 层负责协议转换，业务模块负责规则和操作结果。通知和媒体通过明确接口接入空间业务；后台通知处理依赖已提交事件。依赖在启动时装配，运行时连接、日志与供应商配置集中管理。

## 数据与并发原则

PostgreSQL 保存账号、成员、积分流水、余额、购买快照、操作审计、幂等记录和通知事件。余额为查询使用的当前值，每次修改均与对应流水在同一事务中完成。原始流水保留；撤销和退款形成反向流水。为来源操作与流水种类建立唯一约束，防止同一次回退生效两次。

首版采用**按空间串行提交业务写操作**：在事务中先锁定空间行，再读取成员资格、当前状态和余额，完成修改后提交。加入、退出、记分、购买、退款及商品修改共用这一入口。多个空间可以同时处理，单个小空间内的短事务依次完成。这个选择让退出与购买的生效顺序易于验证；同空间写入增长时，用锁等待指标判断是否需要更细的锁。

空间事务内部的调用都使用同一个事务连接。事务只执行数据库操作；图片、验证码发送及其他外部请求由独立流程处理。锁等待有上限，失败时回滚并按同一操作标识重试。读取需要同时展示余额和多项状态时，使用单条查询或一致的读取快照。

幂等记录与业务结果在同一事务提交。相同操作标识的并发请求由数据库唯一约束协调；客户端断线后仍以持久化结果为准。具体规则见 [API 规范](api.md)。

## 账号与未来客户端

内部 `user_id` 表达一个人；登录身份独立保存渠道、渠道主体及绑定关系。空间成员引用内部账号。每次绑定新的登录身份都验证双方身份，保持原有成员、余额和购买归属。

邮箱验证码验证后取得或建立内部账号，换手机时验证同一邮箱即可恢复原账号。使用服务端可撤销的随机会话凭据：客户端持有高熵随机值，数据库保存其摘要、账号和到期时间。每次业务请求验证会话和资源权限。有效期为 30 天，退出登录立即撤销当前会话；到期后重新验证邮箱。验证码和频控原则见 API 规范，供应商按国内与海外邮箱送达验证选定。

小程序接入时，新增微信登录身份验证和客户端实现，沿用内部账号、空间规则和 HTTP 契约。客户端类型只影响接入能力，业务权限按账号及空间参与状态确定。

## 图片与通知

上传流程为“验证当前权限 → 创建上传记录 → 上传图片 → 服务端验证文件 → 标记可用 → 业务引用”。限制文件类型、实际大小和解码尺寸；展示文件移除定位等无关元数据。对象标识由服务端生成，读取图片时按引用它的资源及当前访问权限签发短期地址，历史购买中的图片沿用历史资源的访问规则。对象存储供应商的具体接入方式在选择后确定。

购买快照引用当时图片版本；仍被历史引用的图片保留。未被业务引用的临时上传可按清理规则删除。

通知沿用[已确认设计](../design/notifications.md)：事务内写事件，提交后处理；事件与接收者唯一标识保证站内记录去重。首版 worker 可与 HTTP 服务同进程运行，通过数据库领取任务及重启恢复。渠道配置、授权与投递结果归通知模块管理。
