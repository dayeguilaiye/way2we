# Flutter 编码规范

状态：阶段 3.1 已获用户采纳。技术组合见[工程方案](architecture.md)，业务反馈见 [API 规范](api.md)。

## 代码与状态

功能目录采用 `features/<feature>/`，按内容建立 `data/`、`application/`、`presentation/`。数据访问负责 DTO 解析与请求，状态控制器负责加载、提交及刷新，Widget 负责展示和用户输入。简单功能按职责保留少量文件，复杂逻辑随实际复用提取。

Riverpod 管理共享依赖和异步状态。控制器使用明确类型及不可变状态，读取和提交状态分别表达。JSON 解析集中在 DTO；解析失败形成可诊断的协议错误。格式与命名遵循 Effective Dart。

所有空间数据状态都包含 `user_id` 与 `space_id`。切换账号清理前一个账号的状态和凭据；切换空间结束旧页面的订阅与请求，并丢弃迟到响应。个人主题归账号所有，在该账号的各空间共用。退出空间后及时清除该空间的活动数据与可用入口。

余额、购买状态和权限以服务端结果为准。客户端可预览积分变化，成功提交后刷新余额、购买详情、近况和通知等受影响查询。用户切换空间期间完成的请求，只更新原请求所属空间。

## 网络与错误

统一 Dio 实例负责基础地址、凭据、超时、请求编号读取和错误解码。数据层将网络异常转换为明确类型：`ApiFailure`、`NetworkFailure`、`TimeoutFailure`、`ProtocolFailure`。错误对象保留稳定错误码、字段错误和可用的请求编号，页面通过集中映射获得文案及下一步行为。

控制器拥有一次提交的操作标识和提交状态，提交期间禁用同一按钮。响应成功后再展示完成；超时保留表单并核对操作结果。底层重试必须保持原操作标识和参数，具体行为见 API 规范。取消客户端请求只终止等待，随后仍可能需要核对服务端结果。

业务接口的 401 由会话协调器统一处理，同时失败的多个请求只触发一次登录引导。验证码验证的 401 留在验证码流程；退出登录时会话已失效则完成本机退出。登录成功后恢复安全的页面位置；涉及积分和状态修改的操作由用户确认继续。同一邮箱恢复原账号，切换到其他账号时独立处理待核对操作。

组件根据自身职责展示反馈：字段错误紧邻输入，业务拒绝在当前任务中说明，结果不明提供核对状态。一个失败只展示一次，网络层将结果交给页面而不直接弹提示。

## 路由与界面

使用 `go_router` 集中定义四个主入口、详情页与登录跳转。路由参数传资源标识，页面加载时重新读取并校验权限；通知入口按资源种类映射到路由。购买等敏感操作依然走当前权限和状态校验。

主题色、字体层级、间距与装饰素材集中定义，使用 `ThemeData` 和有类型的主题扩展供组件读取。个人主题更新时保持页面位置和表单内容。视觉基准见 [DESIGN.md](../../DESIGN.md) 和[参考图目录](../design/visual-reference.md)。

页面具备加载、内容、空、错误和提交状态。检查系统文字缩放、小屏、键盘、安全区域、系统返回及读屏描述。完成与取消按钮沿用已采纳原型的层级和简短标题。图片展示固定占位比例，并处理加载失败。

## 本机存储与资源

会话凭据使用 `flutter_secure_storage`，退出登录时删除。主题等低敏偏好可持久化；缓存按账号隔离。业务提交要求联网，未确认操作只保存必要的核对信息并设明确生命周期。

图片上传通过媒体接口完成，用户可看到进度、失败和重新选择。上传结果使用服务端分配的对象标识；临时访问 URL 按过期时间重新获取。开发日志按[运行规范](operations.md)脱敏，正式构建保留必要诊断信息。
