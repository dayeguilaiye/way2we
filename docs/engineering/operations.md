# 日志与运行规范

状态：阶段 3.1 已获用户采纳。现有服务器与域名在国内，需要时可开通海外服务器。先期工作优先复用现有服务器和 PostgreSQL，控制基础服务费用；数据库部署形态、正式部署地区及对象存储、邮件供应商在接入前补充。

## 日志字段与级别

服务端使用 `slog` 输出一行一个 JSON 事件到标准输出，由部署环境收集、轮转和限制容量。字段名使用 `snake_case`，事件名稳定，例如 `http_request_completed`、`notification_job_failed`。

| 范围 | 字段 |
| --- | --- |
| 每条日志 | `time`（UTC）、`level`、`msg`、`event`、`service`、`environment`、`version` |
| HTTP 完成 | `request_id`、`method`、`route`（模板）、`http_status`、`duration_ms` |
| 有业务身份或错误 | 经过验证的 `actor_id`、`space_id`，安全的 `error_code`、`error_kind` |
| 后台任务 | `event_id`、`job_id`、`attempt`、`duration_ms`，可用时保留 `origin_request_id` |

数据库操作记录保存来源请求编号；通知事件带上来源编号，worker 自己记录任务尝试。`request_id` 关联一次网络请求，业务操作标识关联多次重试，事件标识关联异步处理。

| 级别 | 使用范围 |
| --- | --- |
| DEBUG | 临时开发诊断，正式环境默认关闭 |
| INFO | 请求完成、正常业务拒绝、可预期的生命周期事件 |
| WARN | 可恢复的依赖异常、任务将重试、需要观察的运行状态 |
| ERROR | 未预期失败、panic、任务重试耗尽、数据一致性检查失败 |

一次 HTTP 请求由入口统一记录完成事件，发生故障时将安全诊断字段附在该事件上。底层向上传递错误上下文。worker 为每次任务尝试记录结果，避免同一错误在调用链每层重复出现。

余额不足示例：

```json
{
  "time": "2026-09-28T08:00:00Z",
  "level": "INFO",
  "msg": "request completed",
  "event": "http_request_completed",
  "service": "api",
  "environment": "staging",
  "version": "example",
  "request_id": "req_example_01",
  "method": "POST",
  "route": "/v1/spaces/{space_id}/purchases",
  "http_status": 409,
  "duration_ms": 18,
  "error_code": "INSUFFICIENT_POINTS"
}
```

示例路由与首轮 OpenAPI 一致。路径日志使用模板，业务标识按需要单独记录，便于检索和控制字段。

## 信息与访问控制

采用日志字段允许列表。会话凭据、验证码、Cookie、邮箱全文、约定内容、图片内容及完整请求／响应正文禁止进入日志。对象存储签名 URL 和数据库连接串按凭据处理。SQL 诊断保留操作名和 SQLSTATE 等安全字段，原始驱动错误经脱敏后记录。

客户端正式构建记录错误种类、版本、路由模板及可用请求编号；网络拦截器的正文日志关闭。开发环境也使用虚构数据并遵守凭据脱敏。支持用户复制请求编号用于排查。

技术日志拟保留 14 天并设置磁盘限额，只有维护者可访问。业务历史、积分流水和购买经过存放在数据库，按产品规则保留。验证码与会话数据按各自到期与审计需要清理。

## 配置与部署

配置按本地、测试、正式环境隔离，启动时校验必需项。仓库中的 `.env.example` 只保存键名和安全示例；实际凭据通过环境或部署平台的密钥能力注入。数据库连接池、超时、上传大小、验证码频控和日志级别有明确默认值与可配置上限。

首版一个 Go 服务运行 HTTP 和通知 worker，连接一套权威 PostgreSQL 数据。客户端通过稳定 HTTPS 域名访问，图片与邮件接入各自供应商。先用国内朋友和海外试用者检查实际网络路径、上传及邮件送达，再确定首发环境配置。

测试与正式环境的数据库、图片和邮件配置隔离，每套环境维护明确的数据源。正式环境统一处理国内和海外账号及空间互动；选择海外正式服务器时，整体规划 API、数据库和图片访问路径。现有域名可划分 API 与邮件子域名，按最终供应商配置 DNS。已经承载正式数据的环境迁移时，执行包含数据、图片和会话的迁移及核对计划。

健康检查分为进程存活与就绪检查，就绪包含数据库连接；公网响应仅给出简单结果。停止服务时先停止接收新请求和领取任务，再完成或回滚当前事务，关闭连接。

## 数据库变更与恢复

迁移使用 goose 顺序执行，每次变更带版本并在空库与前一版数据库上验证。已在共享环境执行的迁移保持内容稳定，通过后续迁移演进。部署过程由一个明确步骤执行迁移，运行中的多个服务实例读取兼容结构。

新增字段和结构先兼容当前运行版本，再更新应用；移除旧结构安排独立迁移。发布说明写清结构兼容范围、失败处理和恢复步骤。

测试阶段即建立数据库备份与恢复流程。低预算起步建议每日备份，至少保留最近 7 份，副本放在服务器之外并加密；这对应最多约 24 小时的数据恢复窗口，需要在真实上线前确认是否可接受。每次调整备份方案实际恢复到隔离数据库，核对余额、流水和购买状态。

图片备份与数据库引用一起考虑，历史仍引用的对象参与保留和恢复。演练使用隔离环境，先核验目标连接地址。供应商选定后，在本文补充真实命令和恢复耗时。

## 运行观察

先观察接口失败率、响应耗时、数据库连接与空间锁等待、通知积压和失败、验证码发送失败及磁盘使用。指标标签使用路由、状态和任务类型等有限集合；账号、请求编号用于日志检索。

通知任务记录领取者、租约和重试状态，进程退出后可重新领取。站内通知通过事件与接收者唯一约束去重，投递失败不改变已提交的业务结果。图片清理、验证码到期清理等任务也记录进度与失败结果。
